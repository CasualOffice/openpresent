# 64 — SPK-01: what text in WASM costs

**Status: measured on one machine, for the owner's decision on ADR-004 and ADR-005.**
Code and raw results: [`spikes/spk-01-text/`](../spikes/spk-01-text/), its own Cargo workspace,
which no product crate depends on. Every table below is a selection from
[results/tables.md](../spikes/spk-01-text/results/tables.md), generated by `report.py` from the JSON
beside it.

## Answer

| Question | Result | Recommendation |
| --- | --- | --- |
| Does the shaping stack fit? | **313 KiB Brotli** before fonts, over a 7 KiB baseline | **Accept ADR-004** |
| Is layout fast enough? | 2,000 characters: **0.25 to 0.70 ms** warm in Chrome, 5 to 9 ms for the first layout | Keystroke budget is not at risk from layout |
| Do glyph paths hold a frame? | 200 shapes, about 5,000 glyphs, every shape repainted: **7 to 10 ms** cached on a GPU at 1x and 2x for ordinary text. Without a GPU, 8 ms for Latin but 27 ms for CJK at 1x | **Accept ADR-005, with the conditions below** |
| Do they look right? | Correct and evenly spaced, and visibly lighter than `fillText`, most of all white on dark. Not checked on Windows | Condition: look at it on Windows before Phase 3 |
| Is `fillText` per cluster a fallback? | **No.** It is wrong for Arabic: 78% of clusters drew the wrong form. **Per word** does work | Change the fallback named in docs/42 |

Separately from cost, this measured the reason for ADR-004. With default settings the browser's own
line width for the same text and same font differed by platform: 0 px on macOS and +60 px on Linux
for Carlito, over a 13,172 px run. That is a wrap difference between collaborators.

## 1. Bundle

`release`, no wasm-opt. Each row adds to the one above and includes an export that really uses the
stage, so the linker cannot drop it.

| Build | wasm raw, KiB | Brotli q11, KiB |
| --- | ---: | ---: |
| Baseline: wasm-bindgen only | 17 | 7 |
| + skrifa (outlines) | 397 | 104 |
| + harfrust (shaping) | 790 | 208 |
| + unicode-bidi, unicode-script | 863 | 225 |
| + unicode-linebreak and the spike's pipeline: **the full stack** | 1,228 | **313** |
| Full stack with icu_segmenter, no complex scripts | 1,268 | 326 |
| Full stack with icu_segmenter, auto (Thai and similar) | 1,586 | 610 |
| Full stack + Carlito Regular embedded | 1,841 | 524 |
| Full stack + Carlito and Liberation Sans Regular embedded | 2,243 | 692 |

The JS glue adds 23.7 KiB raw, 3.1 KiB Brotli, at this export surface.

**Fonts, bundled or separate.** Regular faces served separately cost about the same on the wire as
embedding them: 207 KiB for Carlito and 165 KiB for Liberation Sans, so 685 KiB against 692 KiB
embedded. Separate files can be cached apart from the engine and fetched only when a deck names them,
so there is no case here for embedding. All four styles of both families total 1,555 KiB Brotli.
WOFF2 was not measured; the sizes are Brotli over the TTF.

**Tuning buys nothing worth having.** For the full stack, in KiB raw and Brotli: wasm-opt `-O` 1,103
and 315; `opt-level = "s"`, fat LTO, `-Oz` 1,134 and 343; `opt-level = "z"`, fat LTO, `-Oz`, overflow
checks off, 998 and 313. wasm-opt reduced the raw size but not the size on the wire, and the size
profile was larger than release. Throughput below was therefore not traded for size.

**Line breaking is a real choice.** unicode-linebreak has no dictionary, so it does not break Thai,
Lao, Khmer or Burmese inside a run of text. Choosing icu_segmenter's `auto` costs **297 KiB** Brotli
for those scripts. Thai layout itself was not measured.

## 2. Shaping and line-breaking throughput

2,000 characters as one paragraph, 16 px, 600 px measure. Warm figures are per layout, the median of 30
batches of 20. "First" is one layout in a fresh browser with the fonts parsed and no shape plan built,
median of 5. Installed Chrome, `release` then `wasm-opt -O`.

| Text | Glyphs, lines | Bidi + itemize | + shaping | Break opportunities | **Full layout** | With JS copy of arrays | First | chars/ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Latin, Carlito | 1910, 23 | 0.135 | 0.299 | 0.009 | **0.455** | 0.380 | 6.19 | 4,396 |
| Latin, Liberation Sans | 2000, 25 | 0.100 | 0.177 | 0.008 | **0.253** | 0.265 | 5.39 | 7,905 |

full in two rows.

| Full layout, median, ms | Chrome | Headless shell | Node | Native, same code |
| --- | ---: | ---: | ---: | ---: |
| Latin, Carlito | 0.455 | 0.274 | 0.329 | 0.195 |
| Latin, Liberation Sans | 0.253 | 0.198 | 0.240 | 0.156 |
| Arabic | 0.695 | 0.554 | 0.709 | 0.393 |
| CJK | 0.327 | 0.289 | 0.330 | 0.223 |
| Mixed | 0.562 | 0.451 | 0.528 | 0.324 |

The same runs set the first-use costs: instantiating the bundle over loopback takes about 6 ms in Chrome.
`register_font` takes 0.12 to 1.8 ms per face. WASM memory after registering all four faces is 11.7 MB,
because each face's bytes are copied in. The shape-plan cost lands on the first layout of a script,
hence "First". In the headless shell, First runs 8 to 16 ms.

**The pipeline is simpler than the product's will be.** It shapes each paragraph once and breaks on
cluster advances. It does not re-shape at `unsafe_to_break` line ends, and has no tabs, bullets, columns,
autofit, letter spacing or caret table. Re-shaping would add at most about another shaping pass per
paragraph. That is an estimate, not a measurement, and at under 1 ms it does not threaten a 16 ms budget.

## 3. Frame time, dense slide

200 shapes on a 1280 × 720 slide, each with a filled and stroked box and 25 characters. Text sizes run 10
to 14 px across 8 colours. Four texts: Latin (50 distinct glyphs), Arabic (85), CJK from the word list
(136), and **5,000 distinct Han characters** as the worst case for a per-glyph cache. Every shape is
repainted, which is harsher than the editor's drag path, which composites layers ([42](42-TEXT-AND-RENDERING-ARCHITECTURE.md)).

**How to read this.** Canvas 2D is deferred, so timing the JS alone measures nothing: submitting 5,000
glyph fills takes about 1 to 1.6 ms. Each sample is a new canvas ended by its first and only one-pixel readback,
so all drawing must complete. "Cached" subtracts the cost of doing that with nothing painted, which is about
1 to 2.3 ms. **A new canvas is needed because** reading back the same canvas repeatedly gives results in
installed Chrome almost equal to the software browser (Latin 1x, per glyph: 8.24 and 8.50 ms). We infer
Chrome moves a canvas off the GPU after readback; that inference was not separately confirmed.

Cold is that browser's first frame, including outline extraction and `Path2D` construction but not
layout. Median of 3 fresh browsers, since Skia's glyph cache belongs to the process. Cached is a median of
25 in each. All in ms.

| Latin | 1 | `Path2D` per glyph | 16.8 | **7.97** | 13.3 | **8.30** |
| | | `Path2D` per shape | 16.5 | 4.40 | 25.0 | 12.91 |
| | | `fillText` per cluster | 15.2 | 5.67 | 11.4 | 3.62 |
| | | `fillText` per line (reference) | 10.9 | 1.87 | 9.2 | 1.63 |
| Latin | 2 | `Path2D` per glyph | 17.1 | **7.41** | 23.6 | **14.83** |
| | | `Path2D` per shape | 15.8 | 3.80 | 46.5 | 28.16 |
| | | `fillText` per cluster | 17.4 | 5.45 | 18.9 | 6.39 |
| | | `fillText` per line | 13.5 | 1.56 | 14.3 | 3.75 |

| | | `Path2D` per shape | 16.9 | 4.75 | 38.7 | 19.27 |
| Arabic | 2 | `Path2D` per glyph | 16.9 | **8.46** | 29.6 | **20.78** |
| CJK | 1 | `Path2D` per glyph | 20.0 | **10.14** | 35.1 | **26.55** |

Arabic `fillText` per cluster is left out of the conclusions because it draws the wrong thing (§5).
It is in the full tables.

What this shows:

- **The glyph cache works.** Outline to `Path2D` costs 2.5 to 4 ms for an ordinary slide's 50 to 136
  distinct glyphs. A cold ordinary slide costs 16 to 21 ms on a GPU, once.
- **On a GPU, per-glyph paths hold 60 fps** for every text and both DPRs measured.
- **Without a GPU they are the weak case**: 27 ms for ordinary CJK, 21 ms for Arabic at 2x. `fillText` is
  faster there by 1.5 to 4 times for Latin and CJK. This was on an M4's CPU. A slower client would be
  proportionally worse; virtual desktops are the population to worry about.
- **Compound paths per shape are not a free win.** 1.25 to 2 times as fast as per-glyph on a GPU, and 1.3 to 1.9
  times slower in software. Treat them as a later optimisation that needs its own measurement, and do not
  assume them.
- **`fillText` loses badly once the glyph count is high**: 295 ms cold and 32 ms cached against 89 and 13
  for 5,000 distinct Han on a GPU; 234 ms against 36 in software. A dense CJK slide is thus a case for
  paths, against the expectation in docs/42.
- Whole-slide layout, 200 shapes including every array copied to JS: 11 to 21 ms in Chrome. One layout plus one
  cold frame is about 30 to 40 ms on a GPU against the 50 ms slide-switch budget, and about 50 ms for CJK in software.

**Cross-check by `requestAnimationFrame` interval**, with frame-rate limits off and no readback (Chrome, 90
frames): Latin 1x per glyph 6.00, per shape 2.59, `fillText` per cluster 5.18, per line 1.29 ms. CJK 1x per
glyph 7.65. These agree in order with the table. rAF is not necessarily held back by the GPU queue, so they
are a floor rather than the primary figure.

**What I saw, looking at them.**

- **macOS, black on white:** `Path2D` is correct and clean at every size, and lighter. `fillText` looks like a
  slightly heavier weight, at all sizes including 48 px, where this is a platform effect rather than a small-text
  one. At 10 pt 1x both are legible; `fillText` has somewhat firmer stems.
- **macOS, white on dark:** the difference is obvious at a glance. `fillText` looks close to semibold beside
  `Path2D`. `Path2D` looks thin here but is not broken. This is the finding I would want the owner to look
  at, since dark title slides are common.
- **Linux:** `fillText` has LCD colour fringes and hinted, firmer stems at 1x, with **uneven letter spacing**
  because it lands on whole pixels. `Path2D` is softer and evenly spaced. At 2x the difference mostly goes.
- **10 pt at half zoom (6.7 device px):** neither is readable as body text, as you would expect. On macOS
  `Path2D` shows gaps where thin strokes fade. On Linux `fillText` letters collide, "Quarterlyaffinity"
  reading as one word. Neither is clearly better. Thumbnails would need a look of their own.

So on these two platforms it does not look **wrong**. It looks like a lighter weight, and on macOS it differs
from any DOM text beside it. docs/42 has the PNG backend draw the same outlines, so `Path2D` is the choice
that should make the editor match export. There is no such backend yet, so that was not tested.

| Probe | macOS | Linux |
| --- | --- | --- |
| LCD pixels in `fillText` on an opaque canvas, 10 pt 1x Carlito | 0 | 1,814 |
| LCD pixels in `Path2D` | 0 | 0 |

pixel relative to each other, and it cannot be turned off from canvas in what was measured.

## 5. `fillText` as the fallback, and how it disagrees

The test: draw the engine's glyphs for each distinct cluster, and `fillText` of that cluster's characters at the
same origin, 96 px. Compare for shape while tolerating weight (share of each mask within 3 px of the other,
wrong below 0.97). macOS, headless shell and Linux gave the same form counts.

| Text | Variant | Occurrences | Wrong form | |
| --- | --- | ---: | ---: | --- |
| Latin, Carlito and Liberation Sans | Plain | 1623; 1713 | 0; 0 | Ligatures are one cluster, so they survive |
| Arabic | Plain | 1602 | **1249 (78%)** | Each letter draws isolated, [picture](../spikes/spk-01-text/results/chrome-fallback.png) |
| Arabic | ZWJ both sides | 1602 | 1151 (72%) | |
| Arabic | Best of four ZWJ wrappings, chosen per cluster | 1602 | 860 (54%) | Not fixable by wrapping |
| CJK | Plain | 2000 | 85 | All Hangul; see below |

The ZWJ result is the best case of one trick; it is enough to show cluster-level `fillText` cannot carry a
cursive script here.

**Whole-text width, browser minus engine, same string and font, 16 px:**

| Text, engine width | macOS default | Linux default | Linux `geometricPrecision` |
| --- | ---: | ---: | ---: |
| Latin Carlito, 13,172 px | 0.000 | **+60.445** | 0.000 |
| Latin Liberation Sans, 14,281 px | **+10.211** | **−86.992** | 0.000 |
| Arabic, 12,601 px | −0.002 | **−11.229** | +0.013 |
| CJK, 31,565 px | **−215.633** | −23.236 | −31.971 |

Causes found, and how firmly:

1. **Linux default uses hinted advances**: the divergence begins at the first character, and
   `geometricPrecision` removes it for Latin and Arabic. Measured.
2. **Liberation Sans on macOS:** the first divergence is at `of Typ`, a kern across a space. `fontKerning = 'normal'`
   removes it, so the default skips some kerning. Measured. That Blink shapes word by word is the likely reason,
   and was not confirmed.
3. **CJK:** the first divergence is at adjacent fullwidth commas, consistent with Blink's `text-spacing-trim`, which
   was not confirmed. The word list makes adjacent punctuation unusually common, and the macOS figure also
   includes (4), so the size is not representative and has not been broken down.
4. **Silent system fallback.** Noto Sans SC has no Hangul. The engine draws `.notdef` from its stack, and `fillText` draws something
   else without saying so, presumably a system face on macOS; what it drew was not inspected. Measured by the 85 wrong forms, all five distinct Hangul clusters.

Other limits of the fallback: `fillText` takes characters and not glyph ids, so it cannot draw a glyph the engine selected
through a feature it does not know of. Without `direction = 'rtl'`, an Arabic word with a trailing comma put the comma on the
wrong side; this was seen in the first picture and fixed.

**Per word is viable.** `fillText` per whitespace-delimited word, at the engine's word position with `direction` set: the word
widths differed from the engine by at most 0.0001 px for Arabic and 0 for Carlito on macOS; Liberation Sans had 3 of 288 words
over 0.05 px (max 0.88 px) at the default kerning. Arabic looks right in the [picture](../spikes/spk-01-text/results/chrome-fallback.png). Word-level
painting speed was not measured; per-line and per-cluster bound it. If ADR-005 ever falls back, the fallback is:
**`fillText` per word, with `fontKerning = 'normal'`, `textRendering = 'geometricPrecision'`, and `direction` from the engine.**
Word advances under `geometricPrecision` on Linux were not measured individually; the whole-text row above is the evidence.

## Recommendation

**ADR-004: Accept.** 313 KiB Brotli for the text stack, separate from fonts, and layout under 1 ms for a 2,000-character body. For
scale, OpenCalc's bundle is 6.53 MB by its own docs/64, not re-measured here. The alternative was also measured to be worse than it looked: the
browser does not give the same answer across platforms, or even across its own settings.

**ADR-005: Accept glyph paths, with these conditions.**

1. Before Phase 3 closes, someone looks at the same picture on **Windows Chrome**. It is the platform most likely to prefer
   `fillText` (ClearType, hinting), and it is the one not measured. By docs/42's own rule, if it looks wrong there, ADR-005 changes.
2. The owner looks at white-on-dark. If the lighter weight is not acceptable, the next thing to try is compensating `Path2D`
   weight rather than abandoning it. That has not been tried.
3. The fallback named in docs/42 changes from per cluster to **per word**, with the settings above.
4. Software-only clients are recorded as the known weak case. If they matter, the mitigation to measure first is layer and object
   bitmap caching, which docs/42 already calls for.

## Not measured

Windows in any form. Firefox and Safari. Any machine slower than an M4, or CPU throttling. A window on a real display: all
Chrome numbers are headless. A real deck, a real drag, or keystroke to paint end to end. JS heap used by the `Path2D` cache.
Re-shaping at line ends, the caret table, autofit, and variable-font instances other than the default. Thai, Devanagari and
other scripts beyond the three asked for. Bundle size within a real engine: 313 KiB is the increment over a bare bundle, and
the model, import and export crates are separate. Font subsetting and WOFF2. `Path2D` against the tiny-skia backend's pixels.
Appearance with `geometricPrecision` on Linux, whose effect was measured for position only.
